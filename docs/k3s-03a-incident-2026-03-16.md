# Incident Report: k3s-03a Node-Ausfall
**Datum:** 16. März 2026  
**Bearbeitet:** 17.–18. März 2026  
**Severity:** Medium (ein Worker-Node down, Cluster weiterhin funktionsfähig)

---

## Zusammenfassung

Der Raspberry Pi Worker-Node `k3s-03a` (192.168.20.23) ist in der Nacht vom 15. auf den 16. März 2026 gegen 04:18 Uhr eingefroren. Der Node war per Ping erreichbar, SSH und kubelet funktionierten nicht mehr. Nach einem harten Reboot konnte sich der k3s-Agent nicht mehr beim Cluster registrieren. Als Folgeerscheinung fielen die MetalLB LoadBalancer-IPs `.100` (Traefik) und `.101` (Gitea SSH) zeitweise aus.

---

## Ursachen

### 1. Kernel-Freeze auf k3s-03a

Der Pi ist zwischen `04:18` und `04:24` Uhr eingefroren. Der Kernel-TCP-Stack lief noch (Ping und SSH-Port waren erreichbar), aber Userspace war vollständig eingefroren – SSH-Sessions konnten nicht gestartet werden.

Da der Absturz so hart war, dass journald nichts mehr schreiben konnte, sind keine Logs des vorherigen Boots erhalten (`journalctl -b -1` lieferte nichts).

**Indizien:**
- Boot-Partition hatte `Dirty bit` gesetzt → nicht sauber unmounted
- NVMe SMART: 13 Unsafe Shutdowns, aber keine Media Errors
- Exakter Auslöser unklar (Kernel-Bug, Memory-Druck oder IO-Problem)

### 2. Automatische TLS-Zertifikats-Rotation

k3s rotiert Serving-Zertifikate automatisch. Um **00:56 Uhr** wurde `kube-system/k3s-serving` erneuert:

```
Updating TLS secret for kube-system/k3s-serving (count: 16)
```

Nach dem Reboot hatte k3s-03a einen **CA-Hash-Mismatch** – die gecachten Zertifikate im Agent-Verzeichnis passten nicht mehr zur neuen CA:

```
token CA hash does not match the Cluster CA certificate hash:
eeb7028c...  !=  be726e3a...
```

### 3. Alter `k3s-node.service` (Überrest der ersten Installation)

Durch den harten Reboot wurde ein vergessener `k3s-node.service` aktiviert – ein Überrest der ursprünglichen Cluster-Installation mit den alten Management-VLAN-Adressen (`192.168.11.x`):

```ini
ExecStart=/usr/local/bin/k3s agent \
  --server https://192.168.11.135:6443 \
  --token K10eeb7... \
  --flannel-iface=eth0 --node-ip=192.168.11.133
```

Dieser Service startete einen zweiten k3s-Agent-Prozess, der versuchte einen nicht mehr existierenden Server zu erreichen, und **blockierte Port 6444** (lokaler k3s Load Balancer). Der korrekte `k3s-agent.service` konnte sich dadurch nicht initialisieren.

**Erkennungsmerkmal:** Zwei k3s-Agent-Prozesse auf Port 6444:
```
LISTEN  127.0.0.1:6444  users:(("k3s-agent",pid=2574,...))
LISTEN  127.0.0.1:6444  users:(("k3s-agent",pid=929,...))
```

### 4. MetalLB L2Advertisement unvollständig

Die L2Advertisement hatte nur das GMKtec-Interface konfiguriert:

```yaml
interfaces:
  - enp1s0.20   # GMKtec (AMD64) ✅
  # eth0.20     # Raspberry Pi (ARM64) ❌ fehlte!
```

Sobald k3s-03a nach dem Neustart der Leader für eine MetalLB IP wurde, konnte er diese **nicht announen** – sein Interface heißt `eth0.20`, nicht `enp1s0.20`. Folge: `192.168.20.101` (Gitea SSH) war nicht erreichbar.

Zusätzlich antwortete MetalLB auf ARP-Requests auch auf `enp1s0` (Management-Interface), wodurch der UniFi Traffic für `.100`/`.101` über das falsche VLAN routete.

## Durchgeführte Maßnahmen

### Fix 1: k3s-Agent-Zertifikate erneuern

```bash
# Auf k3s-03a:
sudo systemctl stop k3s-agent
sudo rm -f /var/lib/rancher/k3s/agent/client-ca.crt
sudo rm -f /var/lib/rancher/k3s/agent/server-ca.crt
sudo rm -f /var/lib/rancher/k3s/agent/client-*.{crt,key}
sudo rm -f /var/lib/rancher/k3s/agent/serving-kubelet.{crt,key}
sudo rm -f /var/lib/rancher/k3s/agent/*.kubeconfig
sudo systemctl start k3s-agent
```

### Fix 2: k3s-node.service deaktivieren

Auf allen Raspberry Pi Worker-Nodes (k3s-01a bis k3s-05a):

```bash
sudo systemctl stop k3s-node.service
sudo systemctl disable k3s-node.service
sudo rm /etc/systemd/system/k3s-node.service.disabled  # bzw. die originale .service Datei
sudo systemctl daemon-reload
```

### Fix 3: MetalLB L2Advertisement korrigieren

In `gitops/config/metallb/config.yaml`:

```yaml
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: default
  namespace: metallb-system
spec:
  ipAddressPools:
    - default-pool
  interfaces:
    - enp1s0.20   # GMKtec Master (AMD64)
    - eth0.20     # Raspberry Pi Worker (ARM64)
```

### Fix 4: ARP auf Management-Interface unterdrücken

Auf allen GMKtec Master-Nodes (gmkt-01x, gmkt-02x, gmkt-03x):

```bash
sudo sysctl -w net.ipv4.conf.enp1s0.arp_ignore=1
sudo sysctl -w net.ipv4.conf.enp1s0.arp_announce=2

# Persistent:
sudo tee /etc/sysctl.d/99-arp-fix.conf << EOF
net.ipv4.conf.enp1s0.arp_ignore=1
net.ipv4.conf.enp1s0.arp_announce=2
EOF
```

### Fix 5: Git Remote wiederherstellen

Nach temporärem HTTPS-Workaround für git push:

```bash
git remote set-url origin git@git.reckeweg.io:achim/homelab-infrastructure.git
git remote set-url --add --push origin git@github.com:arx666x/homelab-infrastructure.git
```

## Präventive Maßnahmen

### Zertifikats-Rotation robuster gestalten

k3s rotiert Zertifikate automatisch. Nodes die während der Rotation down sind, müssen nach dem Neustart ihre Certs manuell erneuern. Ein Prometheus Alert kann früh warnen:

```yaml
- alert: K3sCertExpiringSoon
  expr: (x509_cert_not_after - time()) / 86400 < 30
  for: 1h
  labels:
    severity: warning
  annotations:
    summary: "k3s Zertifikat läuft in {{ $value | humanizeDuration }} ab"
```

### Node-Down Alerting

Mit dem geplanten Alertmanager-Setup wird ein `NodeNotReady`-Alert nach 5 Minuten ausgelöst – dieser Ausfall wäre dann sofort gemeldet worden statt erst Stunden später zufällig entdeckt zu werden.

### k3s-node.service auf neuen Nodes

Bei zukünftigen Node-Deployments sicherstellen dass kein alter `k3s-node.service` existiert:

```bash
# Prüfen ob Service existiert:
systemctl status k3s-node.service 2>/dev/null && echo "ACHTUNG: k3s-node.service gefunden!"
```
